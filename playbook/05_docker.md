# 05 Dockerで比較できる状態を作る

## 再現レベルを表示する

| レベル | 再現できること | 再現できないこと |
| --- | --- | --- |
| 公開HTML＋資産 | 配信、圧縮、キャッシュ、画面、JS、動画、カタログ | PHP、DB、管理画面、実フォーム |
| 受領PHP＋公開由来の仮データ | テーマ実行、一部クエリ・テンプレート、PHP互換 | 実DB、未受領プラグイン、ACF設定の完全再現 |
| 許可されたテーマ＋プラグイン＋匿名化DB | 本番に近い機能とデータ形状 | 実本番の回線・CDN・負荷等 |
| 本番の段階検証 | 実配信と実ユーザー影響 | 未実施なら完了扱いにしない |

公開情報から製品やダウンロードの仮データを補った環境は、実際の本番DBコピーとは異なる。PHPで描画する経路と保存HTMLを返す経路をURLごとに表示する。

## 構成の基本

```text
利用者 → loopback限定gateway → before / after WordPress
                                  ↘ ローカルDB・仮データ
自動runner → 同じgateway → 条件固定のChromium
手動viewer → 別のChromium → 同じ回線条件、画面を操作
共有公開資産 → 読取専用（秘密・送信処理は置き換え）
```

構成例はDB、変更前CMS、変更後CMS、gateway、runner、viewer。自動試験用と手動確認用のブラウザーは同時に回さない。ローカル公開ポートと各ポートが指す版を台帳に記録する。

## 構築手順

1. 原本を保全し、beforeとafterを別ディレクトリにする。共有する資産は読取専用にする。
2. PHP/WordPress/DB/ブラウザー/Playwrightの版を記録する。ラボの版を本番の版だと書かない。
3. 実メール、購入、WordPress管理操作、外部解析・秘密値を使う連携を無効化する。beforeにも同じ条件を適用する。
4. 内部ネットワーク、loopback公開、専用DB volumeを使う。共有のDBや他案件のコンテナを消さない。
5. 健全性確認、代表URL、404、MIME、Range、圧縮、文字コード、相対参照、カタログ資産を確認する。
6. 初回画像と機能が成立したら、測定前に版の指紋を保存する。測定後に再確認し、途中変更があれば別セッションにする。
7. GUIに「どの版・どの再現レベル・どの回線・初回/再アクセス・未測定か」を出す。

Docker内で `localhost` は利用者の端末ではない。サービス名・公開ポート・ブラウザーから見たURLを分ける。保存サイトの本番絶対URLが残り、外部へ逃げていないかネットワーク記録で確認する。送信ブロックはクライアント側の見た目だけに頼らない。

## 接続権限と起動の注意

試験開始前に必要なホスト・ポート・用途を一覧化する。許可が必要なら実際に必要な範囲だけ依頼し、拒否された経路を別手段で迂回しない。多数の一時ポートを使う設計は接続許可やキャッシュ条件の管理を難しくする。固定gatewayとDocker内の測定を検討する。

ブラウザーを閉じても続く非同期ジョブと状態APIを用意し、二重開始を防ぐ。実行中・完了・失敗・中止を区別する。大量試験を開いているタブのJavaScript寿命に依存させない。

## 手動でUIを見る場合

通常のサイトURLを開くだけではCDPの低速条件は付かない。低速条件を付けたDocker内のブラウザー画面を映し、そのブラウザーへクリック・スクロールを転送するビューアーを用意すれば、UIを見ながら確認できる。

「初回」は新しいコンテキスト、「再アクセス」は同じコンテキスト内の新しいページとする。同じタブのフラグメント移動だけでは新しいアクセスの計測にならない。手動操作には画面転送等の負担が加わるので、自動試験の中央値と混ぜない。静止画像ではなく、動画の時間・ページ送り等で実際に操作できることを確かめる。
