# 07 数字と同時に画面・操作を守る

## 画面を保存する条件

before/afterで同じURL、クエリ、フラグメント、幅・高さ、DPR、スクロール位置、開いているタブ、読み込み完了条件をそろえる。PCと375×667のモバイル幅を確認する。エミュレーションを実機検証と呼ばない。動画、時刻、フォントの描画差などを安易に「差分なし」にせず、差の理由を記録する。

画像差分の閾値を上げて合格にする前に、差の場所を見る。SSIMは画質の指標で、ボタンが押せることや表示時間の証明ではない。ページ画像を縮小比較すると文字の欠落やリンク領域のずれを見逃すことがある。

## 最低限の操作表

| 対象 | 確認する操作・状態 |
| --- | --- |
| 共通 | ロゴ、メニュー、表示幅、フォント、横スクロール、JSエラー |
| 製品一覧 | 初期タブ、切替、画像の遅延読み込み、開閉、ハッシュ直リンク、戻る/進む |
| カタログ | 表紙、次/前ページ、ページ指定、x4拡大、検索、PDF表示、直リンク、戻る |
| ダウンロード | 検索・絞り込み、GETパラメータ、PDF/DXFリンク、空結果、長い一覧 |
| トップ動画 | MP4のまま、自動再生、ミュート、ループ、開始フレーム、進行、モバイル |
| PHP | 投稿なし、画像なし、ACFなし/型違い、存在しないID、記事/製品の代表詳細 |
| フォーム | 別枠で検証。ラボで送信を止めたなら本番相当の送信試験済みとしない |

カタログの `#page=2` が見開きの `#page=3` に正規化されるなど、元の仕様を先に確認する。既存動作を不具合扱いした判定になっていないか、期待値を確認する。試験が落ちたから実装を変える前に、beforeでも同じかを確かめる。

## 画像白抜けから得たこと

画像のcomplete、naturalWidth、HTTP、ファイルSHAが正常でも、表示領域の白抜けを見逃すことがある。観測値だけで表示正常とせず、候補に追加したdecoding等の指定を戻して比較する。古い実装メモより、検証を経た採用版を優先する。

## テストそのものを検証する

- 失敗ケースを故意に与え、テストコマンドが非0終了になることを一度確認する。
- WordPressのfooterを単独で呼ぶなど、実際にない呼出し順で警告を発生させていないか確認する。
- 成功件数の分母を明示する。lint、境界条件、統合確認、操作回帰は別集合であり、合算した数で品質を誇らない。
- 探索的手動確認と自動assertの両方を残す。「画面を見た」はどの画面・操作までかを書く。
- UI確認後にサイト側コードを変えたら、その影響範囲を再確認する。
